# Release Identity Contract v2

This is a targeted Block D deployment-contract amendment for V2.1.0.13. It hardens repository-side release identity only; it does not create or promote a Windows staging release, modify DSH, or provide Windows native evidence.

## Immutable identity

A v2 release ID is `v{version}-r2-{sourceCommit[0:12]}-{artifactDigest[0:32]}`. `sourceCommit` is the lowercase full Asset Hub commit. `sourceArchiveSha256` is retained solely as source provenance: it is never used as the deployable artifact identity.

`artifactDigest` uses `ued-asset-hub-release-tree-v1`. The canonical root is the release directory. Only exact root `deployment.manifest.json` and `deployment.manifest.sha256` are excluded. Every other regular file is recorded as normalized NFC slash path, byte size, and lowercase SHA-256. Records sort by normalized UTF-8 byte order and are hashed as:

```text
UED-ASSET-HUB-RELEASE-TREE-V1\n
<UTF8-path-byte-length>\t<size>\t<lowercase-sha256>\t<normalized-path>\n
```

Timestamps, ACLs, owner, archive/read-only attributes, and empty directories are not identity inputs. Links/reparse points, hard links, unsafe/colliding paths, reserved Windows names, ADS-shaped names, and repository/runtime contamination paths are rejected. Native Windows reparse-point and ADS evidence remains deferred to Block E.

## Manifest and transaction boundary

`deployment.manifest.json` is schema v2 canonical JSON with an exact field set and adjacent `deployment.manifest.sha256`. It binds Asset Hub source provenance, canonical artifact set, pinned external DSH metadata/source fingerprint (not DSH upstream bytes), component hashes, build ID, formal/runtime/operational schema identities, and required evidence types. It contains no timestamp, machine path, run identifier, credential, or secret. Manifest v1 is historical-only and cannot pass v2 production verification.

Its `assetHub` section has exactly three fields: `version`, `commit`, and `sourceArchiveSha256`. Source classification and production eligibility belong exclusively to source snapshot and release provenance evidence, not to the deployment manifest.

Upgrade and rollback topology is not intrinsic release content. A deployment transaction records `fromReleaseId`, `toReleaseId`, checkpoint ID, rollback candidate, both manifest digests, and the compatible Formal DATA/runtime/operational schema versions. Rollback requires that immutable transaction plus verified checkpoint evidence; code rollback is not a Formal DATA rollback.

## Verification

Run `npm run verify:release-identity-contract` (or the retained `npm run verify:windows-deployment-contract`). The isolated fixture covers deterministic rebuild identity, byte mutation, extra/missing files, manifest/DSH/release-ID forgery, v1 rejection, path/link/hardlink hazards, bounded switching, transaction-bound rollback, and source-vs-artifact provenance separation.
