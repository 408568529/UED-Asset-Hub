# V2.1.0.12 Runtime Diagnostics Contract

## Scope

This document defines the only safe diagnostics payload for a future authenticated Admin diagnostics API and report. It does not add process controls, automatic recovery, a health probe implementation, Session governance, or a DSH Source change.

## Compatibility

The existing Runtime top-level status remains `ready`, `starting`, `configuration_required`, `unavailable`, or `error`. `recovering` remains `status=starting` with `phase=recovering`. Shell state remains independent from Agent Runtime state. Existing V2.1.0.11 reason codes and retryable behavior are retained.

## Opaque operation identifiers

`operationId` is a system-generated v4 UUID. It is opaque and must never encode a PID, path, endpoint, command, username, or Secret. The serializer accepts only this UUID shape; any other value becomes `null`.

## Components

The fixed components are `supervisor`, `publicEdge`, `assetHubInternal`, `runtimeControl`, `gateway`, `dsh`, and `proxy`. Their scopes are respectively Runtime Infrastructure, Shell, Shell, Runtime Infrastructure, Agent Runtime, Agent Runtime, and Agent Runtime. Only `assetHubInternal`, `gateway`, `dsh`, and `proxy` are managed child processes.

Component `status` is lifecycle state. Component `health` is evidence from an existing, read-only, no-side-effect health capability. This Contract deliberately does not define an HTTP endpoint, RPC method, port, or probe transport; Block B must confirm the real implementation before wiring probes. Missing or stale evidence is `health=unknown`, never `healthy`.

## Failure and counters

`lastFailure` contains only reasonCode, time, fixed operation type, opaque operationId, generation, nullable exit code, and nullable exit signal. It contains no raw error, stack, process command, environment, path, stdout, stderr, token, cookie, or Credential value.

`restartCount` is per managed child and increments only for a successful replacement child with an integer PID in the current Supervisor lifetime. Initial spawn, failed spawn, and intentional shutdown do not increment it. `recoveryCount` is Runtime-wide and increments once when a recovery operation begins, regardless of how many components it affects or whether it later fails. Both counters reset when the Supervisor restarts; `supervisorStartedAt` identifies the counter epoch.

`diagnostics_retention_failed` is an Observability-degradation reason only. It may make the `supervisor` component health `unhealthy`, but must not change top-level Runtime availability, Shell state, Agent state, retryable state, or trigger recovery.

## Persistence and retention

Live diagnostics state and counters belong to the current Supervisor process. Current process ownership remains in `AGENT_RUNTIME_DIR/supervisor/managed-processes.json`. Lifecycle history remains under `AGENT_RUNTIME_DIR/logs/` and must not be written to `DATA_DIR/meta/logs.json`.

Block B will use a 5 MiB active NDJSON file with at most three rotated files. Rotation must be non-fatal. If rotation cannot complete, the Supervisor records only the fixed Observability-degradation reason and skips further over-limit lifecycle appends until a later rotation succeeds; it must not crash or grow the file without bound.

## Block B instrumentation

Block B implements one Host-owned `RuntimeDiagnosticsState`. It receives only typed lifecycle events from the managed-process controller, Runtime Lifecycle Core state changes and recovery events, and existing read-only health capabilities already used by the Supervisor. It does not add an endpoint, probe transport, watcher, restart strategy, or Runtime Control operation.

The lifecycle writer serializes one allowlisted record at a time. The active `runtime-supervisor.ndjson` is bounded to 5 MiB and retains at most `.1`, `.2`, and `.3`; rotation and retention errors are non-fatal observability degradation. Writer failure does not block the existing shutdown, metadata flush, orphan protection, or lock-release path. During shutdown diagnostics reject new restart/recovery mutations and counter growth, while continuing stopping, exit, health invalidation, ownership finalization, and final stopped states.

## Browser and report boundary

The Browser allowlist is exactly the output of `serializeRuntimeDiagnosticsSnapshot`. A report is generated server-side by serializing that allowlisted shape again. PID, supervisor instance ID, token, Secret, Credential body, cookie, authorization, endpoint, IPC path, command, arguments, cwd, environment, raw error, stack, stdout, stderr, and raw lifecycle records are excluded.

The trust path remains Browser -> authenticated Asset Hub API -> server-side Runtime Control -> Host Supervisor. Diagnostics are read-only and cannot stop, kill, restart, signal, or otherwise control a process.

## Canonical snapshot and report

`parseRuntimeDiagnosticsSnapshot` accepts only an exact output of the Contract serializer and rejects malformed or expanded payloads. It is the canonical parser used after Runtime Control transport; API and UI layers do not recreate the schema. `createSafeDiagnosticReport` consumes that canonical snapshot only, has fixed field and component order, and uses the snapshot's existing `capturedAt`. It does not read the clock, environment, Host state, health capabilities, lifecycle logs, or process metadata.
